§1 — The case

Prompt injection isn't a model problem. It's an authority problem.

An agent that does anything real needs credentials. Today that's a static API key — it does everything the key can do, forever, no matter what the agent was actually asked to do.

Exhibit A — today

The agent reads a ticket, a doc, a web page — text it didn't write. That text contains instructions. The model follows them. It's still holding a key that can refund any order, merge any PR, email every customer, regardless of what the task actually was.

The usual answer is to try harder at the model layer — better prompts, injection classifiers — or add a human approval step that turns into rubber-stamping at scale.

Exhibit B — with Warrant

Authority is derived from the stated task before the agent reads anything untrusted, then signed and time-boxed. The agent's only egress is a broker that checks every call against that warrant.

The injected instruction still convinces the model. The call still gets attempted. It just dies at the wire — not because anything detected an attack, but because that operation was never on the warrant.

§2 — The procedure

Four steps, and the agent never touches a key

Minting requires an operator credential. Calling doesn't. The agent process structurally cannot mint its own authority.

R-1

State the task

A human (or an upstream service) writes what the agent is being asked to do — in plain language, before any tool runs.

R-2

Derive the minimum authority

Gemini reads the task plus your operation catalog and emits the narrowest possible grant set — operations, resource ids, argument bounds, a use budget, a short TTL. It never sees tool output or untrusted content.

R-3

Sign the warrant

The grant set becomes a short-lived, signed token. The agent or MCP client carries this token — nothing else.

R-4

Enforce at the wire

Every call — HTTP /call or an MCP tool invocation — is checked against the warrant. Match: the broker attaches the real credential (or authorizes an upstream MCP) and forwards it. No match: 403, logged with a plain-language reason.

§3 — How to leverage this

Sits in front of what you already run

Warrant doesn't ask you to rewrite your tools. It doesn't ask you to adopt an SDK either.

MCP

Wrap an MCP you already use

GitHub, filesystem, internal tool servers — most already hold a fat service account. Sync their tools into the catalog; Warrant authorizes, then forwards. No changes to the upstream server.

IDE

Scope every Cursor session

A session starts from a task, not a role. The MCP tools it sees are exactly what that task needs — nothing left over for an injected instruction to exploit.

A / B

Split planner and worker

Give the planner a read-only warrant. Mint the worker's mutate warrant only after a human or policy approves the plan. Poisoned research context can't widen what the worker may do.

API

Bring your own HTTP APIs

Declare operations in a JSON manifest — paths, args, which arguments must be bounded. Derivation, enforcement, MCP tools, and the live console all update from one source of truth.

CI

Bound blast radius in CI

A deploy job gets a warrant for one service and one environment. Prod access and secret exfiltration die at the broker, not at a post-hoc review.

LOG

Full attribution, for free

Every decision is audited with who, which agent, which task, and why — allow or deny. Not a feature you bolt on; a byproduct of routing everything through one place.

§4 — Enforcement on record

The broker doesn't need to know what an attack looks like

It performs a lookup: is this operation, on this resource, with these arguments, on the warrant? A wildcard can never authorize a mutation, however the grant came to exist — enforcement doesn't trust derivation, even if derivation is compromised.

§5 — Who is authorized

Anyone whose agent currently holds more than it needs

IDE IDE / Cursor users

You've connected MCP servers with real tokens behind them. Warrant scopes what a given session can actually do, per task.

  • Wrap GitHub, filesystem, or internal MCPs
  • Deny by default; grant only what the task states
A / B Multi-agent builders

Planner / worker / auditor roles that currently share one credential. Give each its own warrant, scoped to its job.

  • Read-only research agents, mutate-capable actors
  • Per-resource scoping so sibling agents can't cross-touch
SEC Platform / security teams

The blocker on shipping agents in a regulated org is usually "we can't give it credentials." This is the layer that unblocks that.

  • Full audit trail: who, agent, task, allow/deny, why
  • Blast-radius bounds on CI and deploy agents
SDK Agent framework authors

You don't want to build an authority model, same reason nobody wants to write their own auth. Register a catalog, inherit derivation and enforcement.

  • Nothing to import — it's a proxy and a token format
  • Works from any language behind MCP or HTTP

§7 — Stated plainly

What this is not

1.
Not a guardrail. A guardrail inspects an action and judges it. This performs a lookup against a signed warrant.
2.
Not a helpdesk product. Sample manifests exercise the mechanism. The product is the authority layer under your tools.
3.
Not "zero network." The agent has no credentials and no unmediated egress — the broker (or wrap process) holds the keys.
4.
Not finished everywhere. Multi-tenancy, key rotation, Ed25519 signing, and org policy above derivation are roadmap.
Closing statement

Stop trying to make the model resistant.
Take the key away from it.

Connect Warrant under the MCP tools you already run — the agent keeps working, the credential never leaves the broker.
